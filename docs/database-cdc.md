# 数据库 CDC / Binlog 同步设计（暂未实现）

> 状态：设计记录，当前版本不实现。

## 当前能力边界

平台现有数据库迁移是一次性全量复制：Worker 分批读取来源表并写入目标表，任务结束后
不会继续消费来源数据库的新增、修改或删除事件。因此当前功能不能称为实时同步，也不能
保证迁移期间持续发生的业务写入最终到达目标库。

现有 `DatabaseTransfer` 检查点只用于全量任务的表级进度恢复，没有保存 MySQL GTID、
binlog 文件与 position、事件幂等键、schema 版本或消费延迟。

## 管理边界

平台不应自动执行 `SET GLOBAL`、修改 MySQL 配置文件或重启数据库来开启 binlog。这些
操作影响整个数据库实例，应由 DBA、云数据库控制面或基础设施即代码完成。平台后续只
负责只读检查前置条件，并在条件不满足时拒绝创建或启动 CDC 任务。

MySQL 前置条件至少包括：

- `log_bin=ON`；
- `binlog_format=ROW`；
- `binlog_row_image=FULL`；
- 配置稳定且不冲突的复制客户端 `server-id`；
- 使用专用最小权限复制账号，不复用数据库工作台账号；
- binlog 保留周期覆盖最大允许中断时间；
- 优先启用 GTID，并记录服务端 GTID 模式；
- 网络策略只允许 CDC 组件访问已授权的数据库实例和内部事件通道。

## 推荐架构

Kubernetes 环境推荐使用 Debezium Server 或 Kafka Connect 负责数据库协议和 binlog
解析，平台不在 API 进程中自行实现复制协议：

```text
MySQL binlog
    → Debezium Server / Kafka Connect
    → Kafka、Redis Streams 或其他持久事件通道
    → 平台 CDC Worker
    → 目标数据库
```

CDC 消费器必须作为独立 Worker 部署，API 只负责配置、审批、状态查询和控制命令。
事件通道必须支持持久化、顺序消费和重放；不能使用进程内存保存尚未落库的事件。

## 同步流程

1. 检查来源数据库类型、版本、binlog 配置、账号权限和保留周期。
2. 创建一致性全量快照，同时取得与快照对应的 GTID/binlog 起始位点。
3. 完成全量数据装载后，从记录的位点开始消费增量事件。
4. 按来源事务顺序应用 `INSERT`、`UPDATE` 和 `DELETE`。
5. 目标事务提交成功后，才提交并持久化消费位点。
6. Worker 重启或网络恢复后，从最后一个已提交位点继续。
7. binlog 已过期、位点不可用或 schema 不兼容时暂停任务，不得静默跳过事件。

## 一致性和安全约束

- 默认目标语义为至少一次投递；目标写入必须基于来源、GTID/事务、表和事件序号生成
  幂等键，重复事件不得产生重复数据。
- 同一表分区内保持事件顺序；跨表事务需要作为一个提交单元处理。
- DDL 默认不自动执行。检测到结构变化后暂停对应表并等待人工确认或映射升级。
- 表映射必须固定主键策略；无主键表默认拒绝增量同步。
- 删除事件必须显式启用，避免配置错误导致目标数据被批量删除。
- 同步凭据使用现有加密密钥环保存，详情接口不得回传，日志必须脱敏。
- 审批、启动、暂停、跳过、重置位点和重新全量同步均写入审计日志。

## 后续数据模型需求

后续实现至少需要独立的 CDC 任务、表映射、消费位点和失败事件模型，记录：

- 来源和目标数据源、数据库及表映射；
- 生命周期状态、审批信息和期望状态；
- GTID 或 binlog 文件与 position；
- 快照标识、schema 版本和最后心跳；
- 已提交事件序号、同步延迟和吞吐；
- 重试次数、错误分类、死信事件及人工处置记录。

CDC 状态不能复用当前全量迁移的自由结构 `checkpoints` 字段作为唯一真源。

## 分阶段实施建议

1. 增加数据模型、配置 DTO、权限和只读前置条件检查。
2. 实现一致性快照与位点绑定，不启动持续消费。
3. 接入 Debezium 和持久事件通道，实现单表、同类型数据库同步。
4. 增加幂等、断点续传、延迟监控、死信和人工重放。
5. 再评估跨类型映射、DDL 协调和大规模分区能力。

在以上能力完成前，产品界面和文档应始终使用“全量迁移/备份”，不得宣称“实时同步”或
“持续同步”。
