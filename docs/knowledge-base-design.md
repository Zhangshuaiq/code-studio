# 团队知识库与 Markdown 文档设计

## 目标

Markdown 文档是团队知识资产，不从属于需求。每个团队天然拥有一个知识库，团队成员可从两个入口访问同一份文档：

- 知识库入口：创建文件夹、技术规范、架构说明、排障手册等通用文档；
- 需求入口：打开与需求关联的详细文档。需求文档必须存放在该需求所属团队的知识库中。

编辑器采用单一所见即所得模式，Markdown 快捷输入会立即转换为对应块。光标进入表格后显示上下文工具，可在当前单元格下方新增行、右侧新增列，以及删除当前行或列。

编辑器采用单一所见即所得模式，不提供源码/预览切换。Markdown 输入规则在空格键后即时转换为块格式（如 `# ` 转一级标题、`## ` 转二级标题），底层保存时仍序列化为 Markdown。左侧大纲与正文之间允许拖拽调整宽度。

需求与文档采用可选的一对一关联。普通知识文档的 `requirementId` 为空；需求详细文档的 `requirementId` 非空且唯一。编辑器、修订历史、权限和审计逻辑只实现一套。

## 领域模型

### KnowledgeFolder

- `id`、`teamId`、`parentId`、`name`；
- `createdById`、`createdAt`、`updatedAt`；
- 同一父文件夹下名称唯一；禁止循环移动；删除非空文件夹前必须先迁移或删除内容。

### KnowledgeDocument

- `id`、`teamId`、`folderId`、`requirementId?`；
- `title`、`contentMarkdown`、`version`；
- `createdById`、`updatedById`、`createdAt`、`updatedAt`；
- `requirementId` 唯一，确保一个需求只有一份权威详细文档；
- 文档移动只能选择同团队文件夹，需求文档不能移动到其他团队知识库。

### KnowledgeDocumentRevision

保存不可变的版本号、Markdown 快照、修改说明、修改人和创建时间。保存使用 `baseVersion` 乐观锁，版本冲突时拒绝覆盖。

## 权限

- 团队成员可读取本团队知识库；非成员不可枚举文件夹或文档；
- 团队任意有效成员可创建文件夹和普通文档；
- 团队成员可编辑文档正文、标题和所在文件夹，所有写操作进入审计日志；
- 创建需求文档还需具备需求读取权限，并验证需求属于当前团队；
- 删除需求关联文档默认禁止，只能解除关联或通过需求治理流程处理，避免需求详情产生悬空链接。

## 页面结构

- `/knowledge`：选择用户所属团队，展示文件夹树和文档列表；
- `/knowledge/documents/:id`：浏览器新标签页中的独立编辑器，不渲染平台 AppShell；
- `/requirements/:id`：只展示文档摘要和“打开详细文档”；首次打开时先选择团队知识库文件夹并创建关联文档；
- 编辑器左侧固定显示标题大纲，顶部显示团队知识库、所在文件夹、创建人、最后更新人及时间；保存时可移动到本知识库的其他文件夹。

## 迁移兼容

现有 `Requirement.contentMarkdown` 和 `RequirementRevision` 先保留用于无损迁移。上线迁移为每个已有需求创建关联的 `KnowledgeDocument` 和对应修订；所有读写切换完成并核对数量与内容哈希后，再在后续迁移删除旧字段，避免一次性破坏已有文档。
