# 需求管理、交付流水线与联调预览设计

## 一、核心边界

需求是方案、排期、负责人、开发分支和联调预览的业务主实体。平台使用全局唯一且不可修改的需求编号作为联调路由标识，例如 `REQ-20260904-A1B2C3`。

隔离分为两层：

- 编辑隔离：仍为 `userId + projectId` 的独立 Git worktree，协作者不会覆盖彼此未提交的文件。
- 联调隔离：以 `requirementNo` 为边界。同一需求的协作者共享一套服务覆盖，不同需求之间完全隔离。

同一需求、同一 `serviceKey` 只能有一个活动预览部署。多人同时开发同一服务时，必须先明确由哪个需求项目分支负责当前联调版本，不能按最后一次点击静默覆盖。

## 二、需求实体

### Requirement

- `id`：数据库 UUID；
- `requirementNo`：不可变全局编号，也是路由标识；
- `teamId`：需求所属项目组；
- `title`：需求标题；
- `summary`：列表摘要；
- `contentMarkdown`：当前 Markdown 正文；
- `documentVersion`：乐观锁版本号；
- `status`：draft / active / completed / cancelled / archived；
- `currentStage`：design / development / testing / canary / release；
- `progress`：0-100，默认根据阶段状态计算，允许需求负责人说明后手动修正；
- `plannedStartAt`、`plannedEndAt`：总体排期；
- `ownerId`：需求总负责人；
- `createdById`、`createdAt`、`updatedAt`。

需求编号由服务端生成，客户端不能指定或修改。编号不包含标题、用户名等可变或敏感信息。

### RequirementRevision

Markdown 文档不能只保存最后一次覆盖结果。每次成功保存产生不可变修订：

- `requirementId`、`version`；
- `contentMarkdown`、可选变更摘要；
- `createdById`、`createdAt`。

第一阶段采用乐观锁：保存请求携带基准 `documentVersion`，版本不一致返回冲突并要求合并。多 Pod 不使用进程内锁。后续如果需要语雀/石墨级多人实时编辑，再引入 Yjs/CRDT、WebSocket Redis 广播和持久化快照；不能把普通 WebSocket 文本广播误称为协同编辑。

需求标题、负责人、排期和状态保存同样携带详情中的 `updatedAt` 作为乐观锁基准，避免两名管理者最后写入者静默覆盖。需求终态变更、阶段最终完成和预览实例注册使用相同的 PostgreSQL 事务级 advisory lock 串行化；预览在 K8s 资源创建后、实例落库前再次校验需求状态、关联负责人、Session 和 `changeRequired`，校验失败则清理本次资源。

### RequirementStage

每个需求固定创建五个有序阶段：

1. `design`：方案设计；
2. `development`：开发；
3. `testing`：测试；
4. `canary`：灰度；
5. `release`：上线。

阶段字段包括：

- `ownerId`：阶段负责人；
- `descriptionMarkdown`：负责范围、交付物和注意事项；
- `status`：pending / in_progress / completed / blocked / skipped；
- `plannedStartAt`、`plannedEndAt`；
- `startedAt`、`completedAt`；
- `sortOrder`。

阶段负责人只能更新自己阶段的内容和执行状态；需求总负责人可以调整排期、负责人和处理阻塞。`release` 完成后需求进入 `completed`。回退阶段必须填写原因并记录活动日志。

### RequirementProject

需求可以关联多个项目，每个关联项表示一个需要开发或参与联调的微服务：

- `requirementId`、`projectId`；
- `serviceKey`：必须与测试环境服务标识一致；
- `developerId`：该项目开发负责人；
- `branchName`：由平台生成 `feature/<requirementNo-lowercase>-<serviceKey>`，实际创建后不可随意改名；
- `sessionId`：开发负责人对应的用户工作区；
- `changeRequired`：是否需要修改并部署；
- `status`：pending / developing / preview / completed；
- `createdAt`、`updatedAt`。

关联项目不代表必须部署。`changeRequired=false` 的服务不创建需求预览实例，路由自然回落到默认测试环境。

## 三、Markdown 需求编辑器

界面参考语雀/石墨的交互结构，并按信息密度拆成三个独立路由：需求列表默认只展示摘要、负责人、状态与进度；点击需求进入流水线和服务拓扑详情；详情中的“详细需求文档”链接通过浏览器新标签页打开专用文档页面，正文不再平铺在需求详情中。文档路由位于平台 AppShell 之外，不渲染左侧菜单、顶部页签或工作区布局，但仍复用登录态与需求读取/编辑权限校验。

专用文档页提供编辑、分屏和阅读三种模式，使用标准 Markdown + GFM 渲染，支持分级标题、粗体、斜体、引用、有序/无序列表、任务清单、链接、表格、行内代码和代码块。一级、二级、三级标题具有明确的字号、间距和分隔层级。顶部固定展示创建人、最后更新人、创建时间、最后更新时间与当前版本；最后更新人和时间以最新不可变文档修订为准。

```text
需求编号 / 文档标题 / 创建与更新信息 / 当前版本
工具栏：H1 / H2 / H3 / 加粗 / 斜体 / 引用 / 列表 / 任务 / 链接 / 代码

┌──────── Markdown 编辑 ────────┬──────── 实时预览 ─────────┐
│ 标题、列表、表格、代码块       │ 渲染后的需求文档          │
│ Ctrl/Cmd+S 保存                │ 目录与标题定位             │
└───────────────────────────────┴────────────────────────────┘

关联项目 / 服务标识 / 开发负责人 / 分支 / 是否需要部署
文档修订历史 / 阶段活动记录
```

需求详情同时提供服务拓扑视图。它按 `serviceKey` 合并关联项目、开发负责人、需求分支、预览实例和有效路由租约，明确展示“需求预览”“预览启动/失败并回落测试环境”或“默认测试环境”。页面只把 Ready 且租约未过期的端点标记为预览路由，不能仅凭数据库中存在预览实例就宣称流量已经切换。

关联项目的实际开发负责人可以直接在服务拓扑停止自己 Session 下的 starting / ready / failed 预览，使需求满足完成或取消前的资源清理条件。停止接口仍要求 `generate:execute` 和 Session edit 权限；主动停止同时写入平台审计日志和带操作者的需求活动。需求负责人和管理员可以查看所有预览状态，但不能借需求权限停止其他开发者的工作区；需要由对应开发者操作，或后续通过独立且可审计的运维回收流程处理。

文档修订历史独立分页读取，默认展示最近 50 个不可变版本的修改人、摘要和时间；需求活动时间线展示最近 100 条负责人调整、阶段更新、项目关联、分支创建、预览部署发起人、主动停止人以及路由 Ready、移除和租约过期事件。路由心跳续租不重复写活动，避免时间线被周期任务淹没。

Markdown 渲染必须禁用原始 HTML或进行严格清洗，链接使用安全协议白名单，防止存储型 XSS。正文设置大小上限，修订历史分页加载。

## 四、需求流水线

正常状态迁移：

```text
方案设计 → 开发 → 测试 → 灰度 → 上线
```

- 创建需求时五个阶段一次性写入同一数据库事务。
- 后一阶段开始前，前一阶段必须 completed 或由需求负责人明确 skipped。
- blocked 阶段必须填写阻塞原因。
- completed / skipped 阶段回退到未完成状态时必须填写原因，原因进入不可变活动记录并触发总进度重算。
- 只有需求负责人可以跳过阶段，且必须填写原因；完成或跳过的阶段进度固定为 100%，待开始阶段进度固定为 0%，进行中阶段最高为 99%，不能只拖动进度制造互相矛盾的状态。
- 测试失败回退开发时，记录回退人、原因和原阶段版本；不删除历史。
- 灰度和上线只表达流程治理，不复用个人预览部署接口；实际共享环境发布仍走部署中心和发布权限。
- 需求编号不是生产部署参数。测试、灰度、生产的共享部署及正常访问不需要需求标签；`X-Codegen-Requirement` 仅由可信的预览联调入口注入。生产网关应清除外部同名 Header，并绕过需求预览路由控制面。
- 总进度按阶段权重计算：设计 15%、开发 40%、测试 25%、灰度 10%、上线 10%。阶段内部可填写 0-100 的进度，需求总进度由服务端聚合。
- 阶段更新取得需求级事务锁后，必须复核需求和阶段的 `updatedAt`；如果请求等待锁期间状态已经变化，则返回版本冲突，不能基于旧的负责人、前置阶段或终态判断继续写入。

## 五、开发分支

开发负责人点击“创建开发分支”时：

1. 校验需求、项目和负责人都属于同一项目组；
2. 获取或创建负责人在该项目的 Session/worktree；
3. 基于开发者当前工作区分支创建 `feature/<requirementNo-lowercase>-<serviceKey>`；
4. 使用仓库级锁修改 worktree 元数据，使用用户工作区锁执行分支操作；
5. 将实际分支名和 Session 写回 `RequirementProject`；
6. 已存在同名分支时必须确认它确实属于该需求，不能直接复用未知分支。

创建新分支时先执行标准 Git `checkout -b`，让未提交修改随工作树进入新分支，再在新分支提交保护性快照；禁止先在来源分支提交用户改动。写回关联前会再次检查需求状态、开发负责人和 `changeRequired`，并通过条件更新声明分支归属。同名分支已经存在但数据库没有归属记录时拒绝自动认领，避免把人工分支误绑定到需求。若 Git 分支已成功创建但最终归属条件更新失败，保留分支和用户内容并明确报错，不能自动删除可能包含代码的分支。

一个用户工作区在同一时刻只能检出一个分支，符合标准 Git 行为。切换到另一需求前必须处理未提交修改。

## 六、需求预览路由

预览资源使用：

```text
codegen.io/requirement-no=req-20260904-a1b2c3
codegen.io/service-key=order-service
codegen.io/project-id=<projectId>
codegen.io/session-id=<sessionId>
```

请求入口使用可信的 `X-Codegen-Requirement` 标识。路由算法：

1. 根据登录身份校验调用者可访问该需求；
2. 对目标 `serviceKey` 查找该需求下唯一且 Ready 的预览实例；
3. 存在则路由到需求预览实例；
4. 不存在则路由到该项目绑定的默认测试服务；
5. 预览实例返回业务 4xx/5xx 时不自动回落，避免掩盖问题和重复写操作。

服务间 HTTP/gRPC 调用必须传播需求编号。具体选择网关、Nacos/Spring Cloud 还是 Service Mesh 适配器，由部署环境决定；平台核心保存统一契约和注册状态，不写死厂商实现。

## 七、权限

- 需求查看：项目组成员；
- 创建需求：具备需求创建权限的项目组成员；
- 编辑正文和总体排期：需求负责人或显式 `admin` 角色；`requirement:manage` 本身仅表示可以创建并管理自己负责的需求，不能作为越权条件；
- 更新阶段内容：该阶段负责人、需求负责人或需求管理员；
- 关联项目和指定开发负责人：需求负责人或显式 `admin` 角色；
- 创建开发分支：只能由对应开发负责人操作自己的用户工作区，且还需项目 edit 权限；
- 部署需求预览：对应项目开发负责人，且需 generate/preview 权限；
- 灰度、上线：继续要求发布权限，不能因担任阶段负责人自动获得生产发布能力。

需求状态只允许 `draft → active → completed → archived`，草稿或进行中可以转为 `cancelled`，取消后只能归档。完成、取消或归档前必须先停止所有 starting / ready / failed 的需求预览；failed 只代表启动检查失败，不代表 Kubernetes Deployment、Ingress 和 Secret 已清理。进入任一终态时会立即删除需求路由端点；进入 completed 时还会把全部关联项目收敛为 completed。该逻辑同时覆盖手工完成需求和完成/跳过最后一个流水线阶段两条路径，不能依赖端点租约稍后自然过期。关联项目的负责人和 `changeRequired` 只能在需求分支创建前调整；分支创建后配置冻结。

需求进入 completed / cancelled 后，正文修订、标题、负责人、排期和项目关联全部冻结，只允许继续转为 archived；archived 完全不可变。阶段跳过仍需满足前置阶段已经完成或跳过，不能通过连续跳过绕过流水线顺序。历史需求因此可以作为稳定的审计快照，而不是继续被原地改写。

所有负责人变更、阶段迁移、分支创建、预览部署和发布动作进入审计日志。

管理员覆盖仍受需求项目组可见范围约束；平台管理员没有被自动加入某个项目组时，不通过需求接口绕过项目组隔离。创建需求分支和部署个人预览始终要求实际被指派的开发负责人，管理员身份不能替代开发者操作其工作区。

## 八、实施顺序

1. Requirement、Stage、Revision、Project、Activity 数据模型和权限；
2. 需求列表、Markdown 编辑与乐观锁修订；
3. 固定五阶段流水线、负责人、排期和进度；
4. 项目关联与标准开发分支创建；
5. 预览运行态关联需求，路由标识使用需求编号；
6. 用户工作区不可变快照构建（已完成静态实现，待部署验证）；
7. 接入实际路由适配器和测试环境回落（控制面解析契约与基础拓扑视图已完成，数据面适配器待部署技术选型）；
8. 如确有多人同时编辑同一文档的需求，再增加 CRDT 实时协作。
